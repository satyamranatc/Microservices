Software Architecture Simplified

Microservices Kya Hote Hain? Bilkul Zero Se Ek Masterclass

Bina kisi complex technical jargon ya hype ke — aasan Hinglish mein samajhiye ki aakhir badi tech companies apni applications ko kaise design karti hain.

EP
The Engineering Pedagogue Naye learners aur curious developers ke liye likha gaya lekh

Agar aap software development ya tech ki duniya mein naye hain, toh aapne microservices shabd zaroor suna hoga. Log isse aise bolte hain jaise ye koi jaadu ki chhadi ho jisse har software problem hal ho jaati hai. Lekin agar aap kisi se seedhe shabdon mein poochhein ki "Bhai, aasan bhasha mein batao ye aakhir hai kya?", toh zyadatar log ghuma-phira kar jargon bolne lagte hain — jaise "loosely coupled", "scalability", ya "service mesh".

Aaiye aaj in saare bhaari-bharkam shabdon ko ek taraf rakhte hain. Aaj ka hamara maqsad ye hai ki hum microservices ko bilkul zero se samjhein. Hum ye maan kar chalenge ki aapne pehle kabhi servers manage nahi kiye hain aur na hi cloud infrastructure dekha hai. Hum ek chote se program se shuru karenge, dekhenge ki jab wo bada hota hai toh kahan rukawat aati hai, aur phir samjhenge ki software ko alag-alag tukdon mein baantna kyun zaroori ho gaya.

Ustaad Ka Niyam (The Guiding Principle)

Software architecture mein kabhi bhi koi "best" tareeka nahi hota. Har design kisi na kisi trade-off (samjhaute) par tikka hota hai. Microservices koi medal ya fashion nahi hai; ye ek zaroorat ke tehat chuna gaya raasta hai jab aapka system bahut bada aur complex ho jata hai.

01. Kahani Ki Shuruat: Monolith Kya Hota Hai?

Microservices ko samajhne se pehle aapko us cheez ko samajhna padega jisko hatane ke liye microservices banaye gaye. Us purane tareeke ko hum kehte hain: Monolith (Monolithic Architecture).

Greek bhasha mein monolith ka matlab hota hai "ek bada, akhand patthar". Software engineering mein Monolith ka matlab ek aisi application hai jiska saara code, saare features, aur saari file ek hi jagah, ek hi project folder mein rehti hain.

Asli Zindagi Ki Misaal
Mohalle Ki Choti Bakery

Maan lijiye aapke mohalle mein ek choti si bakery hai jise Ramesh akele chalata hai. Us ek hi kamre ki dukaan mein Ramesh saara kaam karta hai: counter par customer se order leta hai, piche jaakar aate aur maide ko goondhta hai, oven mein cake bake karta hai, dibbe pack karta hai, aur galle mein paise rakhta hai.

Sab kuch ek hi chhat ke niche hai. Jab koi customer aakar kehta hai "Bhaiya, ek pound cake dena", toh Ramesh ko kisi ko phone karne ya chitthi likhne ki zaroorat nahi padti. Wo turant do kadam piche mudta hai, cake nikalta hai, paise leta hai aur apni diary mein likh leta hai. Ye tareeka tez hai, aasan hai, aur isme koi jhanjhat nahi hai.

Software ki duniya mein bhi har application shuruat mein aisi hi banti hai:

  • Frontend: Jo screen user ko dikhti hai (buttons, forms, pages).
  • Business Logic: Wo code jo calculation karta hai (jaise discount lagana, password check karna).
  • Database Access: Wo code jo ek single database se data padhta aur save karta hai.

Ye saara code ek hi project mein hota hai. Jab developers ko website live karni hoti hai, toh wo ek single file bana kar ek server par chala dete hain. Shuruat ke liye ye tareeka sabse behtareen aur asardaar hota hai.

02. Jab Dukaan Badi Hoti Hai: Monolith Ki Dikkat

Agar Monolith itna aasan aur seedha hai, toh log isse pareshan kyun hue?

Kyunki jab koi cheez choti hoti hai toh chal jaati hai, lekin jab wahi cheez bahut badi ho jaati hai toh wahi simplicity ek gale ki faans ban jaati hai.

Ab sochiye ki Ramesh ki bakery ka cake itna mashhoor ho gaya ki roz subah 10,000 log dukaan ke aage line laga kar khade hone lage. Ramesh ne 25 naye helpers ko kaam par rakh liya. Lekin dukaan wahi ek hi chota kamra hai, jisme ek hi oven hai, ek hi sink hai, aur ek hi galla (cash drawer) hai.

Ab dekhiye software mein aisi haalat mein kya dikkat aati hai:

Pareshani A
Ek Choti Galti Aur Poora System Thapp (The Blast Radius)

Monolith mein saara code ek hi memory space mein daud raha hota hai. Agar naye developer ne "Customer Reviews" wale feature mein koi galti (bug) kar di jisse memory bhar gayi, toh na sirf reviews wala hissa band hoga, balki poori website crash ho jayegi! Log checkout nahi kar payenge, payment fail ho jayegi, aur company ka lakhoon ka nuksaan ho jayega. Ek choti si galti ne poore jahaz ko duba diya.

Pareshani B
Scaling Ka Bekaar Kharcha (Inflexible Scaling)

Maan lijiye aapki website par 95% log sirf products ki photos scroll kar rahe hain, aur sirf 5% log actually payment kar rahe hain. Monolith mein aap sirf photo dikhane wale hisse ko alag se powerful nahi bana sakte. Agar aapko traffic sambhalna hai, toh aapko poori ki poori heavy application ko 10 naye servers par copy karna padega — jisme payment, database connection aur saare bekar features bhi double ho jayenge. Isse paisa aur resource dono barbaad hote hain.

Pareshani C
Engineers Ka Traffic Jam (Deployment Paralysis)

Jab 200 developers ek hi codebase mein kaam karte hain, toh ek doosre ke code se takraav (merge conflicts) aam baat ho jaati hai. Agar kisi engineer ko homepage par ek spelling theek karni ho, tab bhi use poore 5 lakh lines ke code ko dobara test karna padega, 2 ghante build chalana padega, aur raat ko 2 baje deployment window ka intezar karna padega taaki doosre teams ka kaam kharab na ho. Kaam ki raftaar bilkul dheemi ho jaati hai.

Pareshani D
Nayi Technology Na Use Kar Paana (Tech Lock-in)

Agar aapka Monolith 2015 mein Java mein likha gaya tha, toh ab aapka poora system usi par baandha hua hai. Kal ko agar Machine Learning ke liye Python ka koi zabardast tool aata hai, toh aap use asani se use nahi kar sakte, kyunki aapka poora system ek hi purani bhasha mein qaid hai.

03. Solution: Microservices Ka Asli Concept

Yahin par aati hai Microservices ki philosophy.

Ek Microservices Architecture mein hum ek badi, bheed-bhad wali application ko chote-chote, azaad (independent) hisson mein baant dete hain. Har hissa sirf aur sirf ek specific kaam karta hai, apna alag database rakhta hai, aur doosre hisson se network ke zariye baat karta hai.

Ramesh ki bakery wali misaal par wapas aaiye. Ab Ramesh ne ek hi kamre mein sabko bharne ke bajaye, road par alag-alag specialized shops khol di hain:

  • The Pastry Workshop (Baking Service): Yahan sirf cake aur bread banti hai. Inhe customer ke payment ya delivery se koi matlab nahi hai.
  • The Cashier Desk (Payment Service): Yahan sirf paise lene, bill kaatne aur invoice banane ka kaam hota hai.
  • The Delivery Hub (Shipping Service): Yahan orders pack hote hain aur delivery boys ko diye jaate hain.
  • The Accounts Office (User Profile Service): Yahan customer ki membership aur details save rehti hain.

Agar delivery hub ka packaging tape khatam ho gaya, toh pastry workshop mein cake banna band nahi hoga! Agar shaam ko achanak cake ki maang 5 guna badh gayi, toh Ramesh sirf pastry workshop mein 2 naye bhati-baker add karega, cashier counter par faltu log bithane ki zaroorat nahi padegi.

Microservices Ke 3 Sunahare Niyam

Kisi bhi system ko sach mein Microservice kehne ke liye in 3 niyamon ka hona lazmi hai:

1. Single Responsibility (Sirf Ek Kaam): Har service ka ek hi maksad hona chahiye (jaise sirf Payment sambhalna ya sirf Notification bhejna).
2. Independent Deployment (Azaad Rihai): Payment team agar mangalwar ko dopahar 2 baje naya feature live karna chahti hai, toh unhe Order team ya User team se permission lene ki zaroorat nahi honi chahiye.
3. Decentralized Database (Apna Alag Khata): Ye sabse zaroori niyam hai — har microservice ka apna personal database hota hai. Koi doosri service uske database mein direct jhank kar data chura nahi sakti.

04. Naksha: Dono Architectures Ka Fark Dekhiye

Aaiye diagram ke zariye dono models ko aamne-saamne dekhte hain. Dhyan se dekhiye ki Monolith mein database kahan hai aur Microservices mein database kaise alag-alag batte hue hain.

Tasveer 1.1: Monolith mein agar koi ek hissa bhi crash hota hai ya database atakta hai, toh poori application ruk jaati hai.

Tasveer 1.2: Microservices mein har service ke paas apna personal database hota hai. Koi doosra usme seedha hath nahi daal sakta.

05. Ye Services Aapas Mein Baat Kaise Karti Hain?

Ab aapke dimaag mein ek swabhavik sawal aayega: agar sab kuch alag-alag computer par chal raha hai aur sabka database alag hai, toh ye aapas mein coordinate kaise karte hain?

Monolith mein toh seedha ek function doosre function ko bula leta tha: createOrder() ne chargePayment() ko call kiya aur baat khatam. Microservices mein kyunki wo alag-alag machines par hain, unhe network ke zariye baat karni padti hai. Iske do mukhya tareeke hote hain:

1. Direct Phone Call (Synchronous REST / HTTP / gRPC)

Is tareeke mein ek service doosri service ko seedha network request bhejti hai aur jawab ka intezar karti hai:

Order Service kehti hai: "Bhai Payment Service, user ke account se 500 rupaye kaat lo." Aur Order Service tab tak ruki rehti hai jab tak Payment Service ka reply nahi aata: "Haan, paise kat gaye!"

Ye samajhne mein aasan hai, lekin iska nuksaan ye hai ki agar Payment Service kisi wajah se dheemi chal rahi hai ya down ho gayi, toh Order Service bhi wahan atak jayegi.

2. Letter Box Mein Chitthi Daalna (Asynchronous Events & Queues)

Real-world mein mature companies doosra tareeka zyada pasand karti hain: Event-Driven Architecture. Yahan koi kisi ko phone karke pakad ke nahi baithta. Iske badle ek common Post Box (jaise Kafka ya RabbitMQ) hota hai.

"Tamam services ko suchit kiya jata hai: Order #9812 place ho chuka hai."

— Order Service ne Event Bus par notice chipka diya

Order Service turant apna kaam khatam karti hai aur user ko screen par bol deti hai: "Aapka order le liya gaya hai!". Parde ke peeche ab kya hota hai:

  • Payment Service ne notice dekha, bank se paise kaate, aur apna naya notice lagaya: PaymentSuccessful.
  • Inventory Service ne notice dekha aur warehouse mein rakhe item ka stock 1 ghata diya.
  • Notification Service ne notice dekha aur customer ke phone par WhatsApp message aur email bhej diya.

Fayda dekhiye: agar email bhejne wali service 10 minute ke liye band bhi thi, toh bhi checkout nahi ruka! Jab email service wapas start hogi, wo notice board se pending chitthi padhegi aur bhej degi. Kisi ko koi dikkat nahi aayi.

06. Sachayi: Microservices Koi Jaadu Nahi Hain (Asli Mushkilein)

Aksar YouTube tutorials aur promotional blogs yahan aakar ruk jaate hain, jaise Microservices se behtar duniya mein kuch hai hi nahi. Ek sachhe ustaad ki tarah main aapko iska doosra rukh bhi bataunga:

Microservices complexity ko khatam nahi karte, wo bas complexity ki jagah badal dete hain.

Aap code ki complexity ko kam karke network aur infrastructure ki complexity badha lete hain. Jab aap 20 alag-alag microservices chalate hain, toh ye naye sir-dard shuru hote hain:

Monolith Ki Asani
  • Local Memory Call: Function call microseconds mein execute hota hai. Kabhi koi network cable kharab nahi hoti.
  • Simple Database: Agar order fail hua, toh database ek SQL transaction mein sab kuch rollback kar deta hai.
  • Ek Jagah Deployment: Ek file build karo, ek server par daal do. Padhne aur test karne mein asani.
  • Easy Debugging: Ek error aane par pura stack trace ek hi file mein mil jata hai ki kaunsi line par bug hai.
Microservices Ki Musibat
  • Network Latency: Har call network ke raste se jaati hai. Internet ka drop hona ya timeout hona aam baat hai.
  • Data Consistency: Kyunki dono databases alag hain, aap simple SQL JOIN nahi chala sakte. Data match karna mushkil ho jata hai.
  • DevOps Ka Bojh: Ab aapko 1 server nahi, balki 25 alag-alag containers, unke security, aur health check sambhalne padte hain.
  • Bhatakta Hua Debugging: Ek request fail hui toh aapko 10 alag-alag servers ke log files check karne padte hain ki aakhir kaunsi service mein error aaya tha.

Famous software architect Martin Fowler ne is baare mein ek mashhoor niyam diya tha:

"Aapko tab tak microservices ke baare mein sochna bhi nahi chahiye, jab tak aapka system itna bada aur complex na ho jaye ki use Monolith ki tarah sambhalna namumkin ho."

— Martin Fowler, Author of Refactoring and Enterprise Software Architecture

07. Faisla Kaise Karein: Aapko Kya Chunna Chahiye?

Agar aap naya project shuru kar rahe hain ya kisi company mein architecture chun rahe hain, toh is aasan table se faisla kijiye:

Paimana (Criteria) Monolith Chuniye Microservices Chuniye
Team Ka Size Choti team (1 se 15 developers) jo aapas mein roz direct baat karti hai. Badi engineering team (50+ se 500+ log) jo alag-alag office ya shehar mein hain.
Product Ki Stage Naya startup, MVP, ya naya idea jisme agle hafte features badal sakte hain. Established business jahan features ke boundaries (Payment, Shipping, Catalog) pakke hain.
Traffic Volume Normal ya predictable traffic jo aam server se aram se handle ho jata hai. Lakhoon-crodon users, jahan kisi ek feature par achanak 100 guna traffic aa jata hai.
Infrastructure Team Koyi dedicated DevOps team nahi hai; developers hi server dekh rahe hain. Dedicated Cloud & DevOps team jo Kubernetes, Docker aur distributed tracing sambhalti hai.

Duniya ki sabse badi websites jaise Shopify, GitHub, Stack Overflow, aur Basecamp ne saalon-saal apna poora business Monolith par chalaya hai aur aaj bhi unka bohot bada hissa Monolith par hi chalta hai. Unhone day one par microservices nahi banaye the; unhone scale ke sath zaroorat aane par dheere-dheere unhe apnaya.

Aapki Jeb Ke Notes (Pocket Revision)

Agar aap is poore lekh se sirf 5 baatein yaad rakhna chahein, toh ye 5 baatein yaad rakhiye:

  1. Monolith ek bada dabba hai: Saare features ek hi application mein rehte hain aur ek hi database use karte hain. Naye projects ke liye yahi sabse best aur tezz shuruat hai.
  2. Microservice ek azaad specialist hai: Ye ek choti alag application hoti hai jo sirf ek specific kaam karti hai aur apna personal database rakhti hai.
  3. Database kabhi share nahi hota: Agar Service A ko Service B ka data chahiye, toh wo API ke zariye maangegi. Wo doosri service ke database table mein direct query nahi maar sakti.
  4. Baatcheet do tarah se hoti hai: Ya toh direct phone call (REST/HTTP) ya phir notice board par message chhod kar (Kafka/RabbitMQ events).
  5. Ye teams ki azaadi ka tool hai: Badi companies microservices isliye nahi banati ki code fast ho jaye, balki isliye banati hain taaki 50 alag-alag teams ek doosre ke kaam mein rukaavat dale bina tezi se ship kar sakein.
